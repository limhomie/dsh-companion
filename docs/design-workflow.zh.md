# 设计与开发流程

本流程把结构性决策放在编码前解决，把局部实现选择留给短反馈循环。设计原因由 [Agent Note](../.agents/notes/README.md) 保存，长期规则由 [AGENTS.md](../AGENTS.md) 保存。

## 1. 判断改动类型

拼写、机械重命名和不改变行为的局部整理可以直接修改。以下改动属于非机械性工作：用户行为、插件职责、跨 Package 接口、状态所有权、连接生命周期、安全规则、线协议、持久数据、测试策略或构建流程发生变化。

非机械性工作先搜索已有 Agent Note。已经存在决策所有者时更新原 Note；没有时创建 Proposed Note。已经确定并随当前改动落地的决策可以直接创建 Implemented Note。

## 2. 写清问题

`## Problem` 必须脱离方案仍然成立，并回答：谁遇到什么可观察问题、当前行为为什么不足、证据是什么、如果不处理会造成什么后果。

不要把“需要增加某个类、接口或页面”写成问题。那是候选方案，不是用户问题。

## 3. 冻结结构性决策

编码前完成以下设计卡：

| 问题 | 必须得到的答案 |
|---|---|
| 用户结果 | 一条从入口到结果的真实工作流 |
| 所有权 | 谁拥有状态，哪份数据是权威来源 |
| 插件角色 | Definition、Provider、Consumer 分别是谁，是否真的需要拆包 |
| 提交点 | 哪个事件或返回值代表操作已经生效 |
| 失败 | 配置、认证、授权、兼容、传输、过期和业务失败在哪里产生 |
| 生命周期 | 启动、取消、超时、重连、后台恢复、卸载怎样收敛 |
| 外部影响 | 是否改变线协议、持久事件、权限、通知或用户界面 |
| 验证 | 单元、真实组装和浏览器流程分别证明什么 |

包边界、数据所有权或安全模型仍有多个答案时暂停编码。颜色、命名和局部函数拆分等低成本选择可以在实现中决定。

## 4. 比较备选方案

记录真正考虑过的方案以及它们输在哪里。比较维度至少包含：当前用户价值、拥有代码量、协议和迁移成本、安全风险、生命周期复杂度、测试成本，以及是否把未来假设提前固化。

“什么都不做”或“先缩小范围”通常也是有效备选。若实现成本大于当前问题，Agent Note 可以以拒绝或继续 Proposed 结束。

## 5. 先设计证据

在实现前写验收矩阵，不先写测试代码：

| 层次 | 适合证明 |
|---|---|
| 单元测试 | 状态机、投影、校验、幂等和错误映射 |
| Provider 集成测试 | 网络、存储、原生桥接、取消和清理 |
| 真实组装测试 | 插件清单、依赖注入、启动顺序和入口可达 |
| Playwright 流程 | 用户能否在目标视口完成工作，所有状态是否可见 |
| 安全测试 | 未认证、越权、重放、撤销、过期和跨 Origin 拒绝 |

如果现有测试工具无法表达关键场景，先补测试载体，再实现业务功能。

## 6. 实现一条纵向切片

推荐顺序是：最小公共类型与 Service Definition、权威状态和失败类型、一个确定性 Provider、一个 Consumer、真实 App 入口、用户可见流程、文档。每一步都应保持前一步的接口可用，避免同时铺开多个未闭合 Package。

第一条切片应贯穿真实入口，但可以使用 Fixture Provider 隔离尚未完成的远端协议。Fixture 必须遵守与真实 Provider 相同的公共接口和生命周期，不能向 Consumer 暴露测试专用捷径。

## 7. 验证与收尾

运行覆盖改动面的最小充分检查并记录实际命令。失败时先判断是产品行为、测试假设还是工具环境，不通过放宽断言绕过真实失败。

实现完成后把 Proposed Note 改写为 Implemented Note：使用现在时描述实际机制，把验收计划转换为已经存在的验证和后果，删除未实施的未来叙述。PR 只摘要“改了什么、为什么、运行了什么”，不复制 Agent Note。

## 完成定义

一项非机械性工作只有在以下条件同时满足时完成：状态所有者明确；失败和销毁路径有证据；真实入口可运行；用户可见行为有目标视口验证；Agent Note、架构、README 和 JSDoc 与实现一致；没有为了未来假设留下第二份状态或未使用抽象。
