# Agent Note: 用分层决策记录驱动工程实现

Status: implemented

## Problem

Companion 同时涉及 Harness 插件、浏览器客户端、移动生命周期、远程认证和实时事件。若所有约束都堆进一份架构文档，长期规则、当前机制、设计原因和实现计划会混在一起；开发者难以判断哪些内容必须执行，设计变化也容易产生多份冲突描述。若完全依赖编码后评审，状态所有权、安全边界和真实入口缺失通常要通过跨 Package 重构修复。

## Decision

仓库使用四层信息结构：根 `AGENTS.md` 保存每次修改都适用的长期规则；`docs/architecture.zh.md` 和 Package README 描述当前系统与局部接口；Agent Note 保存问题、原因、备选方案和代价；类型、测试及自动化 Gate 执行可以机械检查的约束。一项事实只有一个权威位置，其他位置使用相对链接。

非机械性改动在编码前创建或更新 Agent Note。Proposed Note 必须先确定状态所有者、权威数据、插件角色、提交点、失败位置、生命周期、外部影响和验证路径。会改变 Package 边界、数据所有权或安全模型的开放问题解决前不开始编码。实现完成后，Note 进入 `implemented/` 并改写为当前现实。

实现采用单条纵向切片：从最小 Service Definition 和权威状态开始，接入一个 Provider、一个 Consumer 和真实 App Entry，再增加用户可见流程。尚未存在的远端能力可以由遵守相同公共接口的 Fixture Provider 代替，但不能在 Consumer 中加入测试专用分支。

PR 描述只保存变更摘要和实际验证，不复制设计正文。详细操作步骤由 [设计与开发流程](../../../../docs/design-workflow.zh.md) 持有。

## Alternatives considered

**只维护一份完整架构文档。** 这对初始讨论简单，但稳定原则、当前接口和未来提案会以不同速度变化，最终无法判断哪一段是现状，也无法为具体选择保存落选方案。

**先实现，再在 PR 中解释。** 局部 UI 修改可能有效，但认证、状态和生命周期问题到评审时已经进入多个 Package；PR 关闭后解释也难以成为后续决策的可发现依据。

**每项功能都写完整规格书。** 对小团队成本过高，并会把低成本实现细节过早冻结。本流程只在编码前冻结返工昂贵的结构性选择，其余选择留给实现反馈。

## Consequences

开发者在写第一行功能代码前需要投入一段明确的设计时间，并维护 Agent Note 状态。作为交换，评审可以直接检查状态与安全所有权，功能以真实入口闭环，落选方案不会被反复提出，长期规则也不会随单个功能说明无限增长。

当前流程依靠评审执行，尚未提供 Agent Note 格式、链接或覆盖范围的自动化 Gate。引入代码脚手架时，这些检查应作为独立的仓库工具设计，而不是依赖人工记忆继续扩张。
